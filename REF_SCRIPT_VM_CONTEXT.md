## 2. Command dispatch and stateful execution (T006/T010)
- Registry maps event/call to opcode0, routine to opcode1, save7, wait9, battleEvent10. Missing registry command leaves sentinel 0x80000008 and runtime cleanup/return: source typos chat3/eras/fafeout are ignored, not automatically corrected or syntax-fatal.
- event/call and routine invoke common native 0x4321B0 using different flags/return conventions and scene-dependent event markers; cannot collapse AST operations. wait stores counter at engine+0x1EED58 and resumes per interpreter pass; it is not OS sleep.
- battleEvent replaces the active root list: opcode10 clears engine+0x1EEDB8 with 0x48F620, then appends only ScriptIF roots from the selected event with 0x5299E0. The helper's append behavior is not the whole command's contract; see §4. A normal if is marked in the executed set after its first true result and skipped later, rather than necessarily deleting its list node; rif remains eligible, root false does not run else. Distinct from ordinary scene-event invocation.
- Battle clocks: getTime uses resettable +0x1EED60, isInterval uses absolute +0x1EED64, getLimit uses independent 10-tick cadence. resetTime clears only the former; native isInterval(n>0) rounds n to 10*ceil(n/10). Normal 0x492D80(arg0) root evaluation also lies behind the absolute%10 gate: 0x492FA1 returns to 0x4930A6 when the remainder is nonzero, before 0x4930C0. One battleEvent/DAT plugin tick call is not one internal simulation tick or rendered frame. This follows A72, preserved in [T030 correction](research/recovered/principal_models1/reports/data/T030_RTS_MODE.md#L488); the older T010 claim of first root evaluation at absolute=1 is superseded for this path. BattleWnd arg1's internal loop and pause/UI/render eligibility remain separate. Actual per-scene display/tick outcomes remain VERIFY; the bounded M3 runtime observations are recorded in [MapGimmick §13](REF_MAP_TERRAIN.md#13-m3-アニメーション試験と時間単位の訂正2026-11-09).

## 4. battleEvent replace-all correction

Research ID: `CODEX-BATTLEEVENT-REPLACE-20261109`. Target is the same original ver0.67 PE identified above. This corrects the always-append generalization in [historical findings §19b](research/recovered/findings/PEER_SCRIPT01_FINDINGS_20261011.md#f-19b). An explicit correction is also placed immediately before that historical section; its original claims below the notice remain unchanged.

**STATIC:** after event lookup and temporary body-vector construction, dispatcher opcode10 reloads engine at 0x4A1909, sets ESI=engine+0x1EEDB8 at 0x4A190F, and calls 0x48F620 at 0x4A1915. That helper self-links list head next/prev, zeroes count at list+4, and deletes every old list node (0x48F620..0x48F649). The subsequent loop filters top-level elements to ScriptIF and calls 0x5299E0 at 0x4A195E to append each selected root. Thus the command clears then replaces the root list; only the append helper in isolation is append-only. No mode2 gate appears in this opcode10 branch.

An event that normally resolves to an empty body consequently replaces the list with an empty list. This does not prove behavior of exceptional name-resolution/vector-construction failures. A script that needs two sets of active roots must not rely on two consecutive battleEvent calls accumulating them. The previous assumption that each call preserves prior roots was incorrect.

The normal battle{} registration path at 0x492890 is separately gated by an empty root list; replacing an existing list and initial conditional registration are different operations. A bootstrap root that calls battleEvent from its own body is also not established safe: 0x4930C0 calls the body runner 0x493300 and, on the continuing path, reads the current node's next link. Freeing that current list during the body raises an iterator-lifetime concern. No crash or safety guarantee for that reentrant pattern is claimed here. Existing original-script examples alone do not prove generic iterator safety. The product test correction therefore plans to remove active battleEvent calls and place two rif roots directly in battle{}, delegating reset/step work to routines; this is a proposed test arrangement, not a newly accepted runtime result.

The fresh 0x4930C0 output further distinguishes one-shot execution from node removal. ScriptIF+4 identifies rif, +8 holds the condition, +0xC the then body. Non-rif true roots are added to the executed-set gate (engine+0x1EEDE8 region) and skipped on subsequent scans. This is not proof that their list nodes are deleted. Root list node allocation at 0x4C52D0 is 0xC bytes: next+0, prev+4, payload+8. These are local static findings, not a full scheduler lifecycle proof.

**Bounded runtime observation, separate from causality:** the parent implementation agent reported a read-only inspection of OGG test PID 21760 with root count=1, registered=1, ready=0, map_battle=0, and no HKDR setup call observed. That is consistent with the two-registration test failure, but does not independently prove the complete causal chain or successful replacement behavior in all runtime conditions.
