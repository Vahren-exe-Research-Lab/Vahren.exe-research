# 関数・メモリ事典の追加と訂正

初めて追加する方・AIは、先に[短い追加・訂正ガイド](../CONTRIBUTING.md)を参照してください。このページは形式や例外が必要になったときの詳細です。

対象は迫真戦記 ver0.67。アドレスは原作VAで、基準は0x400000。別版の同じアドレスは別の対象として扱う。

## 調べる

`python tools/reference.py search 解雇` のように日本語、関数名、VA、構造体名で検索する。`--json` を付けると同じ内容をAIから処理できる。ローカルDBや原作EXEのないGitHubクローンでも使える。

## 追加する

1. 既存の symbols.tsv と structs.tsv、関係一覧、研究本文を検索する。同じ発見の別名や後日の訂正がないか確認する。
2. 未収録の研究本文を確認し、個人情報を含まないテキストを research/recovered/ に保存する。原作素材、生成DB、未確認の機密原本は収録対象ごとに判断する。元の相対パスとSHA256、保存版のSHA256を回収台帳へ記録する。
3. 関数名・フィールド定義は既存辞書に追加する。新しい読み書き関係は relations.jsonl に一主張一行で追加する。subject/objectは既存の関数・フィールドの識別子を使う。
4. 各関係に研究本文の相対パス、保存版SHA256、行範囲、対象版、主張の確度を付ける。関数全体の確度をそのまま個別の引数や副作用へ転用しない。
5. `python tools/reference.py build` と `python tools/reference.py check`、既存の辞書検査を実行する。公開許可リストとSOURCE_MANIFEST.tsvにもレビュー済みの追加を反映する。

## 訂正する

過去の説明を覆す場合は、元の主張IDと根拠を記録し、何が変わったかを書いた研究本文を追加する。旧主張を新しい結論と並べて有効扱いにせず、訂正済みの状態と新しい参照先を明示する。確度の引上げは既存の承認手順に従う。

## 確認の意味

生成・検索・SHA検査の成功は記録の整合性を示す。ここで引用する静的解析や実機観測は元研究の確認範囲を保ち、今回新たに原作で再検証したこととは区別する。未収録のログや実験コードは台帳に残す。

## 本文のアドレス言及

回収台帳に記録した本文は保存版SHAを検査し、VAが現れる行を索引化する。辞書にないVAも検索できる。本文での言及は関数の意味を確定する根拠とは分けて表示する。TempStatusWndのような共有レイアウトへの別名は、出典を持つuses_layout関係にaliasesを明記して登録する。

## 略記された出典へのリンク

reference/sources.jsonに出典の接頭辞、収録本文のパスとSHA256、節番号と実在するアンカーを登録する。F§95やC(§93)を解決するには、その接頭辞と節が登録されている必要がある。本文改版時は原本SHAと回収範囲を台帳で追跡し、登録SHAを更新する。不明な略記は未解決として保持する。部分版には除外範囲と手動確認の状態を記載する。

## 定期研究の保存結果と未辞書化のフィールド

回収したRUN_RESULT.jsonは、run・対象VA・タイトル・元の状態・methods内の証拠IDを構造化して検索する。同じVAの失敗と後日の成功は別のrunとして残す。VERIFIEDという元の取得状態を、実機確認や意味の確定へ転用しない。

研究本文のUnit+0x18654やrecord+0x28も、本文の所有者表記・オフセット・出典ごとに検索できる。所有者記号は報告書内の局所文脈であり、そのまま正式な構造体型にしない。実際の型・幅・読み書き関数を確認した段階で、既存の辞書と関係へ根拠付きで採録する。

所有者＋オフセット表記の詳細は所有者ごとに最大100表記で分割する。新しい資料や表記が増えたら索引と詳細ページをまとめて再生成し、旧生成ページが残る場合は確認して整理する。各表記の出典と制約を維持する。

GitHubへのpublish時には、人向けページと本文収録照合表の鮮度検査を自動実行する。辞書や台帳を更新した後はreference.py buildとrecovery_coverage.py buildを実行し、許可リスト・マニフェストも更新する。索引が古い場合は送信を止める。

送信前には、生成ページ・回収台帳と掲載先・引用元・関係の根拠が、許可リストとGitの追跡対象に含まれるかも検査する。ローカルだけに存在する新しい本文やページがあれば、明示的に確認して登録するまで送信を止める。

## 複数原本の回収範囲

本文を読む前に、カタログのメタデータから対象の相対パス一覧を固定し、保留名・対象時間帯・関連研究IDの除外と照合する。本文取得とコピーにはその個別パス一覧を直接使い、広い名前検索から対象を作り直さない。除外対象の読込が起きた場合は対象を収録・抽出・検証から外し、操作監査を残して入力範囲を再固定する。原本の現在SHAと保存版SHA、元の確認区分・訂正・不足する証拠を台帳へ記録する。

## 登録関数の呼び出し関係

`python -B tools/reference.py callers 0x0055BC60 --json` と `callees` で、登録済み関数間のV9静的E8直接CALLを取得する。人向け関数ページにも同じ関係を表示する。`reference/static_calls.tsv` とその出典記録をGitに保存しているため、元SQLiteのない環境でも検索できる。間接CALL・未登録関数・除外範囲は収録対象外。記録当時の照合フラグは今回の独立検証や実機確認を意味しない。

辞書の追加・名称変更では過去の索引を失効させない。新しい静的索引を収録するときだけ、`python -B tools/export_static_calls.py --help` の手順で元データのハッシュと除外条件を照合し、TSV・出典記録・生成ページを一緒に更新する。元SQLiteは任意の再抽出用であり、公開参照物の必須依存にはしない。

## 旧解釈の訂正を検索へ反映する

明示的な訂正根拠がある場合、正本の辞書・関係を確認し、`reference/corrections.jsonl` に対象ID、`status: corrected`、`previous_interpretation`（訂正済みの旧説明）、`current_interpretation`（現在の説明）、要約・確度・対象版・根拠のパス/SHA256/行範囲を記録する。旧説明だけを通常の関係や現行事実として追加しない。対象版は迫真戦記ver0.67で、基準VAは0x400000。

訂正対象は既存の関数・グローバル・フィールドIDを使う。別資料に新説明だけがある場合、過去の誤説明を推測して作らない。元の資料や未収録の根拠を取得できていない範囲も明記する。

同じ主張を再訂正するときは既存の訂正IDを維持し、現在の辞書の解釈・根拠・確度をまとめて更新する。旧版はGitの履歴に残るため、同じ対象・同じ主張について矛盾する「現在の解釈」を並べない。別の誤解を訂正するときだけ別IDを付ける。辞書や本文の改版でSHAが変わったら、全引用行と意味の継続性を確認してから出典記録も更新する。

通常の`search 旧名称 --json`や`search 構造体+0xオフセット --json`で、訂正履歴も取得できる。人向けの[訂正一覧](CORRECTIONS.md)と各関数・フィールドの欄には旧説明を履歴として明示する。`build`/`check`、許可リスト・マニフェストを更新し、元資料なしの別クローンでも同じ訂正と根拠に辿れることを確認する。

## 文書の題名・研究ID・本文を検索する

`search キーワード --json` は、回収台帳で保存版SHAを照合したMarkdown・TXT・JSON・JSONL・TSV・CSV・Pythonコード本文も検索する。題名・ファイル名・研究ID・本文中の日本語など、アドレスを含まない報告にも使える。`reference/DOCUMENTS.md` が全文書の入口になる。JSONの `kind: document_match` は本文の文字列一致であり、関数の意味・型・動作の確定ではない。`source` に一致行・保存版SHAがあり、`recovery` に部分回収・訂正・ID再照合などの制約を保持する。

文書ごとに最初の一致行の最大400文字を返し、文書結果はファイル名の一致、題名の一致、本文だけの一致の順で最大20件。同じ区分内は回収台帳の初出順。これは文字列による探しやすさの順序で、意味の確度や正式採録を示すものではない。`total_document_matches` と `document_matches_truncated`、人向けの省略表示で件数を確認し、研究IDや題名で絞り込む。題名・ファイル名の一致では見出し行（ない場合は先頭行）を示す。アドレス・構造体＋オフセットは既存の専用検索を維持する。JSONの定期実行結果は従来の専用索引で扱う。

対象はGitHubに収録したレビュー済みの本文であり、現在のローカル所在一覧だけにある未確認ファイルは読み込まない。新しい本文はレビュー、台帳登録、`build`/`check`、許可リスト・マニフェスト更新を経て検索へ追加する。同じ保存先を指す台帳行は重複表示しない。

## スクリプトエンジンの基準と型

事典の `ScriptEngine` は、研究でEと呼ばれるGameManager+0x504の埋め込み領域に付けたレイアウト名。原作のC++クラス名を意味しない。`ScriptEngine+0x1EED60` などで検索し、GameManager側の相対オフセットと混ぜない。資料内のE/engineという局所記号は全資料に通じる別名として登録しない。frameInstallMode（追加方法）とexecutionMode（実行モード）も分ける。

辞書を追記した場合、辞書自体を根拠にする関係や訂正のSHAも確認する。既存の引用行が変わっていなければ、その不変を照合してSHAを更新する。引用行や意味が変わった場合は、訂正として根拠・確度・現在の解釈を再確認する。

## 外部チャットからの保全

元がローカルファイルでない回答は、回収台帳の `source_path` に `chatgpt://<chat-id>/messages/<message-id>` を記録する。これは元サービスの出典識別URIであり、研究ROOT内の相対ファイルとして開かない。選択した回答のUnicode本文をUTF-8へ符号化したバイト列をそのまま保存し、そのSHAを `source_sha256` と保存版SHAに記録する。元サービス内部DBや全履歴のバイト一致を主張しない。

題名、message ID、選択範囲、文字数上限、前の回答を読んだか、取得日、個人情報の扱いを捕捉票に残す。最終回答が障害報告なら運用記録と分類し、解析成果数・Golden・現在の自動実行状態へ転用しない。原チャットや自動実行の設定は保全だけでは変更しない。外部出典URIの本文も、台帳の保存版SHA・制約を経て文書検索へ入れる。

## 幅が不明なメモリ項目

根拠に所有者とオフセットの対応はあってもサイズが確定しない場合は、型を `unknown` として不確定範囲を説明に残す。隣接オフセット、整数定数、命令名だけから4バイト・符号型を決めない。研究用の部分レイアウト名は具体的なC++クラスや全callerでの同一性を意味せず、局所記号を全資料の別名にしない。

型・幅が不明な項目はGhidraの構造体反映から除外し、事典・辞書・出典付き関係には保持する。幅を確定した後は新しい根拠と訂正範囲を記録し、通常の追加・検証・再生成を経て型反映の対象へ戻す。元の不明状態はGitと根拠から辿れるようにする。

JSONなどの証拠票は、台帳・レビュー・保存版SHAを通過したファイルだけを通常の文書検索へ加える。非Markdownではファイル名を題名として元の文字列表現と行番号を保つ。JSONを解釈してPASSやmethodsを新しい原作事実へ変換しない。未収録の参照先・未確認の原始証拠・誤りが判明した旧説明は、回収制約から引き続き確認する。専用のRUN_RESULT.json解析は従来どおりで、一般の証拠票とは別に扱う。

検証コードはテキストとして照合するだけで、索引化のために実行しない。引用行は保存ファイルのLF（CRLFを含む）で数え、JSON内のUnicode区切り文字を行の区切りとして数えない。元の保存バイトとSHAは変更しない。

文書が100件を超える場合、GitHubの本文入口は軽量なページ案内にし、出典・SHA・回収制約の詳細を100件ずつに分ける。本文検索の対象や20件の表示上限は変えない。文書数が減って不要な生成ページが残る場合は、checkで検出したものをレビューしてから整理する。
