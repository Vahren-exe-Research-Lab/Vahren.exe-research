## 2. 新発見：Nは任意に大きい引数ではなく、通常経路での再帰深さから生まれる

初期の直接CALLは `0x005D1310` 内の `0x005D140D → 0x005CF4D0`。CALL直前の `0x005D1408 PUSH 0` が第13引数（再帰インデックス）の初期値0で、`0x005D1412 ADD ESP,0x34` は引数13個を示す。検索DBにある対象関数の**直接CALL元は計2件**で、もう1件は自己呼出し `0x005CF628`。原作PEのE8相対アドレスとも一致した。

自己呼出し前の `0x005CF5EE MOV ESI,[EBP+38h]` と `0x005CF5FD LEA EDX,[ESI+1]` は、次のフレームへ **index+1** を渡す。葉側の確保経路 `0x005CF736 MOV EDI,[EBP+38h]`、`0x005CF73C LEA ECX,[EDI+1]`、`0x005CF73F MOV [EBX+34h],ECX` により、確保個数は **N=最深フレームのindex+1**。親は子のCALL成功後に配列を書き、0x005CF628は末尾呼出し最適化ではない。

```text
初期: 0x005D140D → 0x005CF4D0(index=0)
                       └─ 0x005CF628 → index=1
                                          └─ ... → index=L（葉の確保）
葉: N=L+1 を6つの確保サイズに使用。成功後に親 index=L-1, ... 0 へ復帰。
```

これにより「N=134,217,728に達すると32Nが0へ周回」という18Hの**算術的事実**と、その入力経路からそこへ到達可能かという**実行可能性**は別問題だと具体的に切り分けられた。呼出し先の間接経路や改造された入口値はこの結論の対象外。

## 3. 新発見：原作PEは1MiBのスタック予約。サイズ周回よりスタック枯渇が先行する

原作PE32 Optional Headerの `SizeOfStackReserve=0x00100000`（**1MiB**）、`SizeOfStackCommit=0x1000` を機械読み出しした。`0x005CF4D3 SUB ESP,0x70` は112バイトのローカル領域、`PUSH EBP/EBX/ESI/EDI` は16バイト、再帰呼出しサイトでは `0x005CF630 ADD ESP,0x38` が示す引数等56バイトの積み上げがあり、さらにCALLによる戻りアドレス4バイトが必要。すなわち通常の再帰フレーム増分は **188バイト**。`0x38` には13個の引数52バイトと直前から残る一時push4バイトを含む。

単純な予算上限は `floor(1,048,576 / 188) = 5,577` フレームであり、呼出し元やOSランタイムのスタック使用量を無視した**楽観的な上限**。18Hの最初のサイズ周回 `N=134,217,728` には到底及ばない。したがって通常の未改造EXEのこの直結経路では、**整数周回よりはるか手前でスタック枯渇が支配的な上限候補**になる。実際に何千段のOggチェーンを作れるか、スタック枯渇時に何が起こるかは未実測。新スレッドが独自のスタックを指定する場合やPEヘッダを変更した場合にはこの予約容量をそのまま適用できない。

## 4. 追加の6配列境界照合：正常な葉の確保成功と復帰を前提とすれば添字内

葉インデックス `L=N-1` で `+0x38` に `8L+12` まで（DWORD終端 `8N+7`）、`+0x44` に `16L+12` まで（DWORD終端 `16N-1`）を書き、サイズ `8N+8` / `16N` に収まる。親 `i<=N-2` が復帰後に書く6配列の最後のバイト位置（終端はexclusive）は以下のとおり。

| 所有領域 | 確保バイト数 | 親の最大書込終端（exclusive） | 正常条件 |
|---|---:|---:|---|
| `+0x38` | `8N+8` | `8N` | 範囲内 |
| `+0x40` | `4N` | `4N` | 範囲内 |
| `+0x3C` | `8N` | `8N` | 範囲内 |
| `+0x44` | `16N` | `16N` | 範囲内 |
| `+0x48` | `32N` | `32N` | 範囲内 |
| `+0x4C` | `16N` | `16N` | 範囲内 |

特に `0x005CF677–0x005CF68A` の32バイト `REP MOVSD` は `base+32*(親i+1)` へ転送するため、成功した最深フレームNに対して親の最後の転送先は範囲内。見かけ上のone-past配列書込と誤判定しない。比較用の独立整数モデルは `N=1,2,3,7,128,1024,5577` で境界を確認した。**先行17HのNULL未検査（確保失敗時）は未解決のまま**であり、今回の境界成立はmalloc/realloc成功と正常復帰を前提とする。実際の入出力・Goldenではない。
