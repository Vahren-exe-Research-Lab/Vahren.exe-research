## 現状と判断
- 実機確認：GitHub APIで ButaMonky/Hakushin067-Research-Knowledge が非公開・develop既定であることを確認。knowledgeのoriginと一致。

- 判断：今から小さく整理する。現行の汎用一覧・共通ローダー完成を先に進め、GitHub全面移行だけで開発を止めない。
- 比較：研究と製品を単一リポジトリへ統合すると既存知識同期を崩しやすい。現行2領域を分け、拡張コードを1つの製品リポジトリに集める方針を採る。

## 推奨構成（未作成）
既存非公開 Research-Knowledge は検証済み知識・出典・生成ツールを管理する。
別の非公開 HakushinExtensions を拡張コード用に用意する。名称は暫定。
Core、ローダー、DAT汎用UI、雇用並替え、共通API、テスト、ビルド手順を同じリポジトリで管理する。
機能ごとのリポジトリ分割は行わず、共通API変更と利用側を同時に検証できるようにする。
原作EXE/DAT/MAP/ZIP・画像・音声・セーブ・メモリダンプ・巨大生成DB・個人PCパスを含むログは送信対象外。
配布に必要なDAT変更は自作ラッパーと差分適用ツールを基本とし、原作全文は収録しない。

## 着手順
1. 既存ソース・ビルド依存・自作DATの収録候補を明示的な許可一覧にまとめる。秘密情報・原作素材・巨大ファイルを除外する。
2. 現行構成から再現可能なビルドを固める。未整理な作業フォルダ全体を初回履歴に取り込まない。
3. 拡張コード用非公開リポジトリを作成・非公開確認し、レビュー済み初期一式だけを送る。過去のpush禁止は包括委任との適用範囲を整理するまで自動解除扱いにしない。
4. 変更ごとに目的・受入条件・実機/テストのみ/推定を記載した課題を使う。小さな変更単位でレビューし、Windowsビルドと合成テストを自動化する。
5. 現行一覧とローダーを実機受入後、ソースの版と対応した配布物・導入更新無効化手順をリリースとして保存する。

## 委任に基づく実施範囲
- 今行うのは収録範囲・再現ビルド・未完課題の整理。現在の一覧とローダーの完成を、管理環境の全面移行で遅らせない。
- 初回収録候補は data/recruit_sort_v4 の core・src・tests・tools と自作の導入説明。拡張子だけで安全と判断せず、各ファイルの内容と依存先を確認する。
- dist・reports・診断ゲーム・研究作業フォルダは一括登録しない。生成物は検証した配布一式だけを後で版に対応させる。
- 研究事典の既存リポジトリを維持し、製品側の説明から根拠の版・項目を参照する。解析件数と実装完成を区別する。
- 開発課題は「現在の一覧とローダー」「召喚関係の参照」「外部戦闘の受渡し」「簡易戦闘」「戦略処理」「イベント演出」の段階で管理する。今すぐ全段階へ並行着手しない。
- 外部戦闘では勝敗だけでなく生存・経験値・召喚・イベント継続などの受渡し条件を先に確かめる。戦略処理は順序に依存しない計算を見つけてから並列化を判断する。
- 今回は既存の送信禁止を解除したとは扱わず、新規リポジトリ作成・コード送信は未実施。送信する段階で、対象を具体的に示して確認する。

## 目標の階層
現在の完成目標：汎用一覧とローダー。教育・アイテム・人材選択イベントへの導入、取消・安全な復帰、配布を終える。
次の候補：召喚元と子の対応を観測し、同一技能/複数召喚/変身/死亡時の寿命を確認する。経験値配分や技能削除時の対象規則は別々に定義してから実装する。
長期：戦闘の開始状態を外部戦闘へ渡し、結果を原作へ矛盾なく返す。必要な結果項目・イベント・保存互換を先に検証する。
長期：簡易戦闘の正確性と高速化、戦略AI待ち時間短縮、イベント演出追加。
戦略AIの並列化は即断しない。依存する行動順・乱数・共有状態を確認し、計測に基づく高速化を先行する。
大きな機能ごとに別プラグインとするが、未検証の将来用途のために共通APIを先回りして巨大化しない。

## 開発課題にする単位と完成条件
| 段階 | 完成条件 |
|---|---|
| 現行の汎用一覧・共通ローダー | 教育・アイテムの選択、取消、入力分離、更新・無効化・復元を診断コピーで確認し、再現ビルドと導入手順を添える |
| 召喚元・子ユニットの参照 | 複数の召喚元・技能・再召喚・死亡・変身を区別し、関係が消える時点も観測する。経験値還元と技能消去の仕様は別の課題にする |
| 外部戦闘への接続 | まず戦闘開始データを取得し、結果の受渡しと原作イベント継続を最小の試験戦闘で確認する。戦闘全体の再実装とは分ける |
| 簡易戦闘の改善 | 同じ入力で結果と処理時間を比較できる事例を用意し、膠着・召喚・勝敗判定を一件ずつ修正する |
| 戦略処理の高速化 | 時間を占める処理と順序依存を計測する。並列化してもよい計算部分が確認できた場合のみ分離する |
| イベント演出 | DATから呼べる小さな演出を一つ追加し、終了・取消・既存イベントへの復帰まで確認する |

各課題には目的、対象外、担当、変更するファイル、根拠、完了条件、試験結果を記す。
事典を仕様の入口、開発課題を未完作業、リリースを利用可能な版の記録として役割を分ける。
CodexとClaudeは同じファイルを同時編集せず、小さな変更ごとに差分を確認して統合する。
最初は既存の手動ビルドを再現できる状態までに絞り、自動試験や課題の細分化は必要な分だけ増やす。
