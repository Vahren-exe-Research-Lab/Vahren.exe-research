## 2. 新発見A：1回目成功・2回目失敗なら、2回目の値の格納は到達しない

対象の原作実機械語を局所解析した。`0x5964F6`でESIへ対象オブジェクト、`0x596504`で`+0x1C`へ進み、`0x59650A`でその格納先をPUSHし、`0x59650D`で`0x4707D0`を呼ぶ。次に`0x596512`で元オブジェクトをEDIへ戻し、`0x596516`で`[EDI+0x1D]`を求め、`0x59651D`でもう一度`0x4707D0`を呼ぶ。

```asm
0x596504  add esi, 0x1C
0x59650A  push esi
0x59650B  mov esi, ebx
0x59650D  call 0x4707D0          ; destination obj+0x1C
0x596512  mov edi, [esp+0x14]
0x596516  lea eax, [edi+0x1D]
0x59651C  push eax
0x59651D  call 0x4707D0          ; destination obj+0x1D
0x596522  lea ecx, [edi+0x5C] ; only after second call returns
```

`0x4707D0`は4バイト取得処理`0x42E700`を要求したあと、状態を評価する。`0x4707FC`の`JE 0x47081E`で成功経路に入った場合だけ、`0x47081E`でグローバルバッファ`0x00B060E8`の**下位1バイト**を取得し、`0x470824`で出力先ポインタ、`0x470828`で `mov byte ptr [eax], dl` を実行する。

正常成功条件に入らない場合は`0x4707FE`以降の `LoadException`生成と`0x470819 -> 0x5B864E`の例外送出へ進み、`0x470828`の**出力先への書込みは通過しない**。下層`0x42E700`自体が例外を投げた場合も、その呼出しから正常復帰していないため当該書込には到達しない。

従って条件を限定すれば、**最初の値の格納が先に実行された後、2番目の失敗で`LoadException`を送出し、2番目の値は格納されない**という局所の部分更新経路が成立する。共有読込バッファに古い値が残ったとしても、上記の状態失敗経路から`+0x1D`へ古い1バイトを転記する経路はない。これは原作ランタイムでの実測ではなく、命令順序に基づく静的結論である。

**重要な限界**：C++例外アンワインド時のデストラクタ、上位のcatch、状態の再初期化、所有オブジェクトの破棄を**未追跡**。ゲーム中に不完全オブジェクトが残存すると断定してはいけない。今回確認できたのは「`0x5964C0`の通常命令列では二つを一括コミットするのでなく、各ヘルパー成功時に1バイトずつ格納する」ことまで。
