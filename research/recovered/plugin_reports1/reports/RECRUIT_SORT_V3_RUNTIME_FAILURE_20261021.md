# 迫真戦記0.67 人材雇用画面V3 実機失敗・原因研究

- ID: `REDEV-HIRE-SORT-V3-RUNTIME-FAIL-20261021`
- 状態: `GAME_STARTED / UI_DEFECT_CONFIRMED / SORT_FAILED / V3_UNSAFE_FOR_HIRE / FIX_PENDING`
- 原本EXE・DAT・セーブ・Work成果: 変更しない。
- ZIP再作成: 不要。以降は既存フォルダの本台帳とソース・検証結果を更新する。配布必要時のみZIP。
- ユーザー実機観測: V3は起動成功。ゲーム画面がディスプレイ枠を超える／マウス判定がずれる／放浪人材の雇用可能順に並ばない。提供スクリーンショット2枚を根拠とする。
- V3本体の起動前6サイトフック成功＝雇用機能成功ではない。V3は「実機不合格」として扱う。

## P0: 画面DPI異常
- 物理モニター 1920x1200。DPI非対応プロセスからは1280x800と見えており、実際に拡大倍率150%。
- Windows互換性設定 `HKCU/.../AppCompatFlags/Layers` では原本 `Vahren.exe` に `HIGHDPIAWARE`。改名V3 EXEには同設定がない。
- 名前別互換設定の漏れがスクリーン倍率・マウス座標不一致を説明する。有力な原因だが、原本とV3の並列画面比較は未実施。
- ユーザーへの暫定手順: Vahren V3 EXEの「プロパティ」→「互換性」→「高DPI設定の変更」→「高DPIスケール設定の上書き」→「アプリケーション」。この設定確認までは実際の雇用操作を避ける。
- V3 DLLや原本EXE・Windowsレジストリを自動変更していない。

## P0: V3のソート判定が誤り
- V3: `rect_sort_core.h` の `HRS_ALLOW_OFF=0x1480` を0/1の雇用可能フラグと解釈、stable-partition。
- Workの実観測 `hire_ui_live_snapshot_01.json`: 候補17人、press_gate=0が17人。=> V3は全員同一順位でソート効果ゼロ。
- Workの `hire_ui_live_snapshot_02_kmr.json`: 0が16人、1が1人（最初の人）。=> やはり先頭並び替えなし。
- Workの `HakushinHireUI.observation.json`: 原作ネイティブ関係述語 `0x586080` と5人の雇用者を照合し17人中6人を優先。候補順 [6,9,10,11,13,16,0,1,2,3,4,5,7,8,12,14,15]。
- **関係述語だけでは資金・枠・距離を完全判定できない**。表示に「雇用可」と記す前に条件の意味を整理すること。
- Workの別試験では候補内部データとビットマップの並び替え成功にもかかわらず、実際の画面表示に変化なし（後続描画で上書きされる可能性）。

## P1: 描画フック網羅性・状態管理
- Ghidra旧索引で描画関数 `0x4D4A50` の直接CALL6サイトを確認してV3に適用。しかし他チャットのV4機械語監査で `reloadMenu` イベント側の `0x004A5B28`, `0x004A5B54` を追加発見。実際は少なくとも8サイト。旧索引欠落であって新発見を重複計上しない。
- V3 `hooked_renderer` は原処理を呼ぶが、元の `repaint=1` ゲート `this+0xA4 == 0x80000008 && this+0x84 != 0` が偽なら内部で描画スキップ。古い行のRECT/画像を誤処理する危険。
- 原レンダラの `0x130` は横300px、縦5632pxのGDIキャンバス、1行56px。プレゼンタ `0x453C20` のソースは `0x130`、先は `0x118`。改造で呼ぶpresentが他の処理に後から上書きされ得る。
- 100件上限、C++ std::string所有の元ID配列などには触れない。元描画とマウス判定の同期・並べ替え寿命を計測する必要がある。

## 判定の意味を分離
- エンジン `+0x1480` は現在の操作状態を反映する行ごとの押下ゲート。未選択時に全0となる。人材雇用の「誰かが雇える」優先判定に使わない。
- `0x586080`: ECX=対象人材定義、ESI=雇用者定義、AL=雇用関係判定。Work実機で呼出成功。5人の雇用者についてOR集計すれば優先候補が得られる。
- ただし、この述語は資金・人材上限なども含む最終雇用確定処理ではない。入出力/副作用を静的追跡し、実際に採用可能と断言しない。
- Work保有 `dev_lab/src/hire_ui_observation.c` は実機検証実績あり。**read-only参照のみ**としWork所有ソースは変更しない。

## 次の修正依存関係
1. DPI対策を独立検証する。V3用EXEだけ高DPI対応とし、元EXEと画面表示・クリック領域を比較。
2. 独立診断専用（ソート無効）で画面を開き、どのCALL siteが動くか、描画ゲート、現在の候補件数/行ゲート・RECT/画面バッファ状態を計測する。診断による重複再試行禁止。
3. 雇用者（複数）→対象人材の正しい関係述語を画面表示順計算へ渡す。元のC++文字列、雇用ルール、セーブには介入しない。
4. 描画後の更新・再描画による上書きを追跡し、最新の最終フレームとクリック/ホバーの整合が保たれることを実機で証明。イベント `reloadMenu` 2サイトも別途確認。
5. 雇用関係だけでなく資金不足/距離/枠制限も含めるか、ユーザーが求める「雇用可能」の意味を最終確認（現方針は同領地で雇える人材優先）。
6. 実ゲームテストで、クリックした人材ID、金額、所属・雇用者、セーブロード、表示の順序維持、画面スクロール・UI DPI整合を観察。
