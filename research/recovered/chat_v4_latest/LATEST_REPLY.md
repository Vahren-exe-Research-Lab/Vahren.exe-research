V4の報告書と解析ZIPを、プロジェクトLibraryから取得できました。V2・V3の研究資料とも照合できる状態です。

今回の発見で特に重要なのは、**フックの網羅性と、実際の画面更新の網羅性は別問題**だという点です。

`0x004D4A50` への直接CALLを8箇所すべて捕捉できても、候補の生成・クリック処理・選択状態の更新まで完全に捕捉できるとは限りません。

したがって、次の研究では「8箇所を捕まえる」ことに加えて、「候補がいつ作られ、いつ破棄され、どのタイミングで並び替えを適用すべきか」を解明する必要があります。

## 追加解析で確認できた点

原作EXEの機械語とGhidra擬似Cをさらに突き合わせ、次の処理順序を確認しました。

| アドレス | 処理 |
|--------|--------|
| `0x004D6056` | 生成された候補数をウィンドウへ一度格納 |
| `0x004D605C` | 候補数が100を超えるか判定 |
| `0x004D6061` | 超過時に100へ制限 |
| `0x004D606F` | 制限後の件数を書き戻す |

これは重要です。**100件へ切り詰める前の候補数が、一時的に存在します。**

さらに、描画関数では候補を一時的な連結リストに集めてから表示処理へ進む構造も確認できます。

つまり、100件以上を扱う将来の改良では、固定配列を拡張する以外に、**候補リストの段階で抽出・順序を調整する方式**を検討できます。

ただし、各候補の最終的な雇用可否は表示用の処理中にも判定されるため、まだ全候補を安全に雇用可能順へ並べ替えられると証明できたわけではありません。

## 新たに発見した索引の問題

V4の補助SQLiteを集計すると、`reloadMenu` に関連する欠落は、描画関数への2件だけではありませんでした。

`0x004A5AF1～0x004A5BA0` の範囲には、機械語上の直接CALLが **12件**あり、12件とも既存Ghidra CALL索引では未採録でした。

さらに、DATイベント実行関数 `0x004A1250` の内部を集計すると、次の結果になりました。

| 指標 | 件数 |
|--------|--------|
| 機械語由来の直接CALL候補 | 847 |
| Ghidra索引との一致 | 209 |
| 未採録 | 638 |
| 索引一致率 | 約24.7% |

未採録の637件が `0x004A27A4～0x004A61D6` にまとまっており、単発の見落としではなく、**関数内の広い範囲が索引化されていない可能性**が強くなりました。

原因がGhidraのコード認識なのか、参照抽出スクリプトなのかは未確定です。ただし、今後のDAT命令拡張研究では、この区間を補助索引と照合することを必須にすべきです。
