## 結果
1. 実測：save1・save2 は既存パーサーで 1 バイトまで一致して読めた。
   - save1: numeric 3181、Unit 9107、Spot 138、Power 29、外交の Power 参照 25、graph 121/160/11。先頭 u32×5＝(5, 6666, 21, 23, 45)
   - save2: numeric 3288、Unit 9108、ほか同じ。u32×5＝(5, 6666, 22, 1, 14)
2. 実測：save3・auto は "unknown trailing data beyond world graph" で止まる。本体（numeric〜world graph）は読めていて、その後ろに余りがある。
   - save3: 本体の平文 3,653,269 バイト＋余り 2,202,309 バイト（ファイル長は save1 と同じ 5,855,610）。numeric 3857、Unit 5536、u32×5＝(18, 6666, 31, 0, 19)
   - auto: 本体 3,653,335 バイト＋余り 2,436,479 バイト。numeric 3857、Unit 5536、u32×5＝(18, 6667, 1, 0, 54)
3. 実測：余りは「前に書かれた、もっと長いセーブの残り」。
   - 余りの部分について、28 で割った余りごとに最頻のバイトを古い鍵とみなすと（平文に 0 が最も多いため）、save3 では鍵の 28 バイトがすべて 8〜119（原作の鍵の範囲）に入り、その鍵で戻すと Unit の記録らしい平文（"m_wate"、"seiretsu2"、"bara"、"build"… と int32 の組）が読めた。
   - これで T014 A18 の「OPEN_ALWAYS で切り詰めないので、短く上書きすると古い末尾が残る」が実ファイルで起きていると確認できた。
   - auto は同じ方法で 1 つの鍵では戻らない（推定：長さの違う古いオートセーブが何世代も重なっている）。区間に分けて鍵を求める必要がある。
4. 未確認：原作のロードがこの余りを無視するか。読込み側（0x45E1E0 のあと）は world graph の終わりで止まるはずだが、ゲームで save3 を読めるかは確かめていない。
