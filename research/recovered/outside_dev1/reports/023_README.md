# Hakushin Core x86 ABI fixture

Run `./build_test.ps1` from PowerShell. Zig 0.14.1 is resolved relative to this directory. Each compile uses `zig cc -target x86-windows-gnu -Wall -Wextra -Werror`; DLLs add `-shared`, host adds `-municode`.

This is a standalone handshake/lifecycle fixture supporting up to 32 initialized plugins, not the production discovery loader. `HakushinCore_Load` accepts only an explicitly caller-authorized drive-absolute wide-character path. Authorization is a caller assertion, not a security boundary. Caller policy must approve the exact file before invoking this API. Native code and DllMain execute before descriptor inspection. Dependency search uses the plugin directory plus Windows system directory; these must be trusted.

ABI v1 is x86 cdecl, native Windows C layout, exact struct sizes and version, ASCII IDs of 1–63 letters/digits/dot/underscore/hyphen. Callers supply valid accessible pointers; structures start with size/abi. Export lookup uses undecorated names. The ABI1 API still contains logging only. An optional versioned reservation extension now provides metadata ownership checks, not actual hook installation; see HOOK_EXTENSION.md. UTF-8 log strings are borrowed for the duration of the callback. The log callback must remain valid through successful shutdown.

All Core and bound extension calls use the nonblocking ownership gate in CORE_THREADS.md. Competing threads receive existing BUSY immediately with unchanged outputs; callers handle BUSY. Callbacks must return normally. A lifecycle guard rejects nested Load and Shutdown calls with HK_BUSY throughout loading, logging, plugin callbacks, cleanup and FreeLibrary. This lifecycle guard remains separate from the atomic thread ownership gate. The plugin API pointer remains valid from successful initialization until shutdown. Query performs no persistent initialization. Failed init must release all resources. If no tracked reservations remain, Core returns HK_INIT_ERROR (6) and unloads as before. If extension reservations remain, Core returns HK_SHUTDOWN_ERROR (8), retains the DLL/API/token and blocks new loads until explicit shutdown cleanup succeeds. Tracking cannot detect unregistered native patches or threads. Successful init keeps the DLL loaded. Shutdown must stop work and release resources before returning success. Failed shutdown retains the module and API for retry. Caller must call shutdown successfully before unloading Core; process termination is the final fallback. DllMain performs no lifecycle work. No crash isolation, forced cancellation or automatic recovery is provided.

Fixture variants cover descriptor size/version rejection, init failure, wrong plugin ID, and shutdown failure followed by successful retry. Host checks caller size/version, denied authorization, bounded ID, relative-path rejection, duplicate load rejection, actual module residency before/after shutdown, and repeated shutdown. Missing DLL returns a load error. The initial test failed because Core was absent; then all fixtures passed with the implementation.

The separate manifest layer parses the allowlist and plans dependency order; the bootstrap layer connects that plan to this Core after all-file x86 PE preflight. See BOOTSTRAP.md and build_bootstrap_test.ps1 for ownership and rollback semantics. Reservation ownership is now centralized through the optional extension; actual hook patching, event lifetime integration and production discovery remain later work. No game files are patched and no game process is launched or attached.

Multi-plugin lifecycle: each successful plugin owns a fixed slot and stable API pointer until successful shutdown. Duplicate active IDs, duplicate DLL module handles and capacity exhaustion return HK_BUSY. Load failure leaves earlier plugins active; the caller decides whether to continue or request shutdown. Shutdown visits slots in reverse initialization order. On failure, the failing slot and every earlier slot remain resident, and new loads are blocked until a shutdown retry finishes. This preserves dependencies only when the caller initially supplies dependency order. Use `./build_multi_test.ps1` for two actual DLLs with distinct IDs and log callbacks. It checks duplicate rejection, failed-new-init preservation, API pointer stability, failed top shutdown, resident dependencies, retry order and a new load after complete shutdown.
